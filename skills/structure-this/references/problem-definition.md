# Problem definition

## The rule

Before any analysis starts, the problem gets defined in five steps, in order:

1. **Starting point and context** — the system or situation as it stands
   today.
2. **Disturbing event** — what changed to turn this into a problem worth
   analysing.
3. **R1** — the current, undesired result.
4. **R2** — the desired result.
5. **Convert steps 1–4 into a single question** — the question the rest of
   the analysis must answer.

This is the leverage point of the whole method (ch. 8): a badly formed
question invalidates every analysis that follows it. Get the question wrong
and no amount of downstream rigour recovers it — you produce a well-structured
answer to the wrong problem.

## How to test it

Once the question exists, ch. 8 offers four structuring tools for the
analysis itself — pick whichever fits what the question is actually asking:

- **Diagnostic trees** — for finding the cause of R1.
- **Models of the system's structure** — for understanding how the pieces
  that produce R1 relate to each other.
- **Sequence of events** — for problems that are really about what happened,
  in order.
- **Logic trees for generating alternatives** — for choosing among possible
  responses to R2.

The work from here is hypothesis-driven, not exhaustive data collection: form
a specific hypothesis the question suggests, then go find the data that would
confirm or kill it — don't gather everything available and look for patterns
afterward.

## Failure modes

Two errors ch. 8 names specifically:

- **Organising the analysis around the tools available**, rather than around
  the question — reaching for a familiar framework or dataset and forcing the
  problem to fit it, instead of deriving the tool from what R1→R2 actually
  requires.
- **Presenting data instead of conclusions** — a wall of findings with no
  synthesis (see `synthesis-test.md`) telling the reader what the data means
  for R2.
